How a tool call crosses the perimeter

An agent never touches a service, a credential or the network. It proposes a call over one file descriptor; a governor decides; a throwaway executor acts. Pick a scenario and step the packet through. Gold badges mark attestation points: places where something is cryptographically verified before traffic may continue.

untrusted trusted confined, per call attestation point (numbered in the table below)

    The boundaries

    Four of them, each enforced by something different, so that one failure does not collapse the rest.

    Worker ↔ governor kernel

    The only channel is a socketpair(2) the governor created before the worker existed, inherited as fd 3. There is no port, no URL, nothing to discover.

    • Every message carries kernel-stamped SCM_CREDENTIALS; a sender whose UID is not the worker's is dropped and the worker killed.
    • The worker runs as its own user and, with -sandbox bwrap, inside a namespace with no network interface.
    • Its environment is three variables. No proxy settings, no Vault address, no keys.

    Governor signatures

    The trust anchor. Standard library plus one vendored policy engine (Cedar), so the whole thing can be read.

    • Refuses to start unless the manifest and every .cedar file verify against the operator's Ed25519 key. The private key never leaves the operator's machine.
    • Decides from structural facts only: role, tool, target, call count, taint, delegation depth, egress scan level. Never from the agent's prose.
    • Holds no service credential and no backend token. A compromised governor can authorise wrongly; it cannot harvest secrets.

    Executor token + sandbox

    A fresh process per allowed call, in its own bwrap namespace, with the governor's decision carried as a signed 5-second token it verifies itself.

    • Sees its own binary, the governor's public key and two socket files. No interface: the proxy socket is the only way out.
    • Verifies the token's signature, window and binding (tool, target, args hash) before doing anything; exits 2 otherwise.
    • Holds the credential for one call and dies with it.

    Egress allow-list

    Two gates on everything that leaves: a content scan before the decision, and a host allow-list at the wire.

    • Outbound arguments are scanned for credential shapes and for values the governor itself issued (redaction placeholders, token ids). High and active hits are a hard deny.
    • The proxy verifies the per-call token and checks host:port against the tool's signed egress_hosts. Refusals are logged with tool, task, token id and host.
    • Sensitive inbound fields are redacted to [redacted:tok_…]; the real value comes back only through a human-gated detokenize.

    Why the traffic looks like this

    Why a Unix socket proxy instead of a network namespace with iptables

    A namespace with a REDIRECT rule has routes, an interface and a firewall backend to get right, and a mistake is silent. A sandbox with no interface and one socket file has nothing to misconfigure: Unix sockets are filesystem objects, so they cross the network-namespace boundary while TCP cannot. A reviewer can see the entire egress boundary by listing one directory.

    Why the token is checked three times

    The executor, the sidecar and the proxy each verify the same signature with the same public key, and each adds its own check (binding, single use, host list). The governor's decision is therefore not a message to be trusted but a capability to be proven, and a forged or replayed request fails at whichever gate it first reaches. The tests cover replay (exit 3), swapped arguments, wrong tool and a rogue signing key (all exit 2).

    Why the agent's justification is never an input

    Prose is the attack surface. Policy sees only structural facts; the approver sees them first too, and reads the agent's justification only after pressing j. Same facts give the same verdict regardless of what the agent says (test plan M-7).

    What is still outside the PoC

    The sandbox is as strong as the kernel; production keeps a VM boundary around the host. The proxy sees host:port, not URLs (TLS is opaque to it, which is why the scan runs on the arguments beforehand). Delegation between agents and the MCP bridge are week 5.
